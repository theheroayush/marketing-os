## 2024-05-18 - [HIGH] Fix Stored XSS via HTML Escaping
**Vulnerability:** User inputs like profile names (`p.name`) and team member emails (`email`) were being injected directly into the DOM via `innerHTML` without sanitization. This allows for Stored Cross-Site Scripting (XSS) if malicious payloads are saved in local storage.
**Learning:** In vanilla JavaScript applications utilizing template literals with `innerHTML` for rendering, failing to sanitize untrusted user data exposes the application to serious XSS vulnerabilities.
**Prevention:** Always implement and enforce a global HTML escaping utility function (e.g., `app.escapeHtml`) to sanitize any dynamic, user-controlled data before it is rendered to the DOM using `innerHTML`.

## 2024-10-18 - Prevent Stored XSS from Truncated User Input in History View
**Vulnerability:** Truncated user message content (`s.messages[s.messages.length - 1].content.replace(/<[^>]*>/g, '').slice(0, 120)`) was rendered directly into the DOM using `innerHTML`. While regex tag stripping was present, it isn't completely robust and could allow Stored XSS from malformed tags if saved. Also, slicing before escaping is necessary to prevent splitting HTML entities, but the string wasn't escaped.
**Learning:** Even when user input is stripped of HTML tags using regex, it must be escaped (e.g. using `escapeHtml()`) before being injected into the DOM via `innerHTML` to prevent potential bypasses (like Stored XSS). Truncation (e.g. `.slice()`) must occur *before* escaping to avoid splitting HTML entities.
**Prevention:** Always wrap regex-stripped, untrusted user content in a global HTML escaping function (e.g., `app.escapeHtml()`) before rendering it via template literals injected through `innerHTML`.
