## 2024-05-18 - [HIGH] Fix Stored XSS via HTML Escaping
**Vulnerability:** User inputs like profile names (`p.name`) and team member emails (`email`) were being injected directly into the DOM via `innerHTML` without sanitization. This allows for Stored Cross-Site Scripting (XSS) if malicious payloads are saved in local storage.
**Learning:** In vanilla JavaScript applications utilizing template literals with `innerHTML` for rendering, failing to sanitize untrusted user data exposes the application to serious XSS vulnerabilities.
**Prevention:** Always implement and enforce a global HTML escaping utility function (e.g., `app.escapeHtml`) to sanitize any dynamic, user-controlled data before it is rendered to the DOM using `innerHTML`.

## 2026-09-10 - [HIGH] Fix Stored XSS in Chat History Snippets
**Vulnerability:** In `app.js`'s history view rendering, user-generated chat message content was being injected into the DOM via `innerHTML` after only regex tag stripping (`replace(/<[^>]*>/g, '')`) and string slicing (`slice(0, 120)`). Regex tag stripping is insufficient and brittle. It does not escape HTML entities, making it susceptible to bypasses (e.g., malformed tags or attributes). Since these messages are saved in `localStorage`, this resulted in a Stored Cross-Site Scripting (XSS) vulnerability.
**Learning:** Never rely solely on regex to strip HTML tags for sanitizing untrusted inputs. Regex is often incomplete and fails to cover all edge cases of HTML parsing. Furthermore, when truncating strings before injecting them into `innerHTML`, it's critical to apply proper HTML entity escaping *after* all string manipulations to prevent XSS payloads from executing.
**Prevention:** Always wrap untrusted user input with a robust HTML escaping function (like `app.escapeHtml`) before inserting it into the DOM using `innerHTML`, even if the string has been stripped of tags or truncated. Always apply the HTML escaping as the final step before injection.
